普通 Markdown 是「写完就定死」的文本；MDX 则会把 `.mdx` 文件编译成真正的 React 组件。标题、列表、表格这些 Markdown 语法照常工作，同时可以混用 JSX。这篇演示本框架支持的几类高级用法，建议打开源码对照着看。

## export 本身就是 MDX 能力

每篇文章开头的 `export const metadata` 已经是最典型的例子：纯 `.md` 没有任何导出机制，元信息只能依赖 frontmatter 这种「约定格式」；MDX 里它是货真价实的 JavaScript 导出，框架在构建期直接读取。本文所有示例都不需要额外安装任何东西。

## 行内 JSX：给文字上样式

Markdown 的行内元素就那么几种，MDX 里可以直接写 JSX 并搭配 Tailwind 类名——这一段里就有一个<span className="rounded bg-accent/15 px-1.5 py-0.5 font-medium text-accent">样式完全自定义的高亮</span>，没有借助任何额外组件。

适合偶尔强调关键词。但别沉迷：满屏彩色文字的文章没法读，Markdown 语法能表达的就不要动用 JSX。

## 折叠块：details 与 summary

HTML 语义元素在 MDX 里直接可用，比如放一段不干扰主要读者的展开内容：

<details>
<summary>点开查看：折叠内部的 Markdown 照常渲染</summary>

这里的 **加粗**、`行内代码` 和[链接](https://mdxjs.com)都会正常渲染。诀窍是 `<summary>` 标签和内容之间要空一行，里面的 Markdown 才会被解析；标签本身要顶格写，缩进反而会被当成代码块。

</details>

## 花括号是构建期表达式

花括号里可以放任意 JavaScript 表达式，构建时求值一次，产物里就是静态文本。比如这一句里的构建日期是 {new Date().toISOString().slice(0, 10)}——静态导出后被冻结成字符串，dev 模式下则每次请求实时计算，可以当作「这个页面出自哪次构建」的时间戳。

JSX 注释也能用，适合在文章里给自己留备忘：

{/* 备忘：本行演示 JSX 注释，构建后读者看不到它 */}

然后正常写正文——读者永远看不到备忘的内容，这正是注释该有的行为。

## 从数据生成列表

列表项来自一组数据时，不必手写重复的 Markdown，直接 map：

<ul>
{["remark-gfm：表格、任务清单与自动链接", "rehype-slug：为标题生成锚点", "rehype-pretty-code：Shiki 代码高亮"].map((item) => (
  <li key={item}>{item}</li>
))}
</ul>

这是构建期执行的循环。条目又多又结构化的时候，改一处数据比改 N 行 Markdown 可靠得多。

## 还能 import 组件

文章顶部可以像普通模块一样 `import` 站内组件——理论上可以给某篇文章配一个专属的交互控件。本篇刻意不演示：示例文章要零依赖地长期存在，而组件是会重构的。真要用的时候，把标准的 `import X from "@/components/X"` 写在 metadata 旁边就行。

## 三个必踩的坑

1. **裸的花括号和小于号会被当成 JSX**。正文里想写数学式或字面量时，把它们放进行内代码（如 `a < b`、`{count}`），或在符号前加反斜杠转义（`\{` 与 `\<`）。本文里所有原样出现的花括号都做了处理。
2. **JSX 块要顶格**。缩进四格的 `<div>` 会被 Markdown 当成代码块，元素就不渲染了。
3. **标题里别写 JSX**。目录按行提取标题文本，混入标签只会得到一目录的残渣。标题保持纯文本，最多加行内代码。

## 什么时候该用

一句话判断：**内容问题用 Markdown，结构问题用 MDX**。表格、强调、代码块，Markdown 又快又可读；需要样式、折叠、循环或构建期计算这类「结构」时，才动用 JSX。把全文都写成 JSX 等于放弃 Markdown 的可读性，那不如直接去写组件。
